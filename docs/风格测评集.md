# 风格测评集

用一组固定样例，量化「生成结果像不像本人」。这套东西**只做评估**：不改生成链路，不新增草稿 / 改写 / 自评 / 重排，也不做两段式生成。`--run` 每条样例只调用一次当前模型，走的是 `src/llm/client.js` + `src/persona/prompt.js` 的真实构造路径。

## 边界

- 只读 `tests/fixtures/style-eval/samples.json` 和当前配置 / 画像；默认不写任何文件。
- `--check` 不读配置、不构造模型，可以在 CI、本地、没填 Key 的机器上跑。
- `--run` 需要可用的聊天模型；没有 Key 或模型被设为 mock 时直接失败，不会偷偷换成本地假数据。
- 不判断回复「对不对」「有没有用」，只判断表达风格。内容正确性看别的测试。
- 不把测评样例当训练语料：样例最好从风格画像的学习语料里**留出**，否则分数会偏高，测到的是「背过没有」。
- 测评把模型放在「本人」的位置：`them` 是对方，`me` 是本人。提示词仍走现有助手人设 + 风格画像，不会新增「你是本人」的身份指令；这是现有生成链路的边界，不是测评脚本另写的。
- `--run` 沿用当前 `persona.styleMode`。线上用 `mimic` 就用 `mimic` 测，否则分数比较的是 `adapt` 输出。

## 命令

```powershell
# 只校验格式和脱敏规则：exit 0 表示通过，exit 1 表示有问题
node scripts/eval-style.js --check

# 调用当前模型逐条生成并打分；低于阈值 exit 1
node scripts/eval-style.js --run

# 指定样例、输出指标明细、改阈值
node scripts/eval-style.js --run --samples tests/fixtures/style-eval/samples.json `
  --json artifacts/style-eval.json --min-score 65

# 调试时只跑前 5 条（分数不代表整套，不要拿来下结论）
node scripts/eval-style.js --run --limit 5
```

| 参数 | 作用 |
| --- | --- |
| `--check` | 校验样例格式与脱敏规则，不调模型 |
| `--run` | 逐条生成并与 `reference` 比对 |
| `--samples <path>` | 样例文件，默认 `tests/fixtures/style-eval/samples.json` |
| `--json <path>` | 指标明细；只含指标与 id，不含任何消息正文 |
| `--min-score <n>` | 总分阈值 0~100，默认 60 |
| `--limit <n>` | 只跑前 n 条，仅供调试 |

退出码：`0` 通过；`1` 样例不合格 / 模型失败 / 分数低于阈值；`2` 参数用法错误。

## 样例格式

`samples.json` 是数组，每条：

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `id` | string | 2~41 位小写字母 / 数字 / 短横线，全文件唯一 |
| `scene` | string | `work` / `friend` / `family` |
| `context` | array | 1~12 条 `{ role: "them" \| "me", text }`；**最后一条必须是 `them`** |
| `reference` | string | 本人当时真正发出去的那条回复（脱敏或合成占位），不超过 400 字 |
| `notes` | string? | 可选，只写风格说明，不写隐私，不超过 200 字 |

`them` 是对方，`me` 是本人（也是生成时要扮演的一方）。`reference` 是本人对最后一条 `them` 的回复。

示例（合成内容，不是真实聊天）：

```json
{
  "id": "friend-01",
  "scene": "friend",
  "context": [
    { "role": "them", "text": "周末去爬山不" }
  ],
  "reference": "去啊，几点集合？",
  "notes": "有问句，语气轻"
}
```

## 怎么扩充样例

1. 从本人真实聊天里挑一整条回复，**不要润色**。把「当时真正发出去的话」原样留下；模型生成的、事后觉得更礼貌的版本都不能当 `reference`。
2. 脱敏后再写入：
   - 人名 → `老王` / `小李` / `张姐` / `表姐`；
   - 公司 → `某公司` / `甲方`；
   - 地点、门牌、车牌、链接、订单号、金额中的可识别部分 → 删掉或改成泛称；
   - 禁止真实 wxid、群号、手机号、邮箱、公司真名。
3. 三个场景都要有，当前基线是 work 8 / friend 8 / family 8。单个场景少于 3 条会被 `--check` 拒绝。
4. 刻意覆盖不同长度和语气：一句话回复、多行回复、带语气词、带 emoji、拒绝、关心、纯确认。全是「好的收到」会让指标失去区分度。
5. 改完先跑 `--check`。它会复用 `scripts/privacy-scan.js` 的规则再扫一遍，并额外拦「不是以某开头」的公司名。
6. **不要为了提分删掉失败样例**。失败样例才是回归的价值；要改的是生成链路，不是测评集。

## 指标与权重

所有指标都是确定性的：只要 `reference` 和生成文本不变，结果不变。句子按换行和 `。！？!?…；;` 切分；逗号不切，避免把一句话拆成一堆伪短句。长度按 Unicode 字符数算（中文一个字算 1）。

| 指标 | 定义 | 差值与容差 | 权重 |
| --- | --- | --- | --- |
| 平均句长 | 所有句子长度的平均值；语料级把所有样例的句子合并算 | 相差 8 字时子分 0，线性递减 | 0.16 |
| 句长方差 | 句子长度的总体方差（字²） | 相差 60 时子分 0 | 0.06 |
| 问句比例 | `?` / `？` 的数量 ÷ 句子数，封顶 1 | 相差 30 个百分点时子分 0 | 0.11 |
| 语气词密度 | `啊呀吧嘛呢哦噢哈嘿诶唉嗯啦咯嘞呗` 的出现次数 ÷ 100 个非空白字符 | 相差 6 个/100 字时子分 0 | 0.14 |
| emoji 比例 | 含 emoji 的句子数 ÷ 句子数 | 相差 30 个百分点时子分 0 | 0.09 |
| 高频短语覆盖 | 参考回复的 top-5 短语里，原样出现在生成结果中的比例 | 直接作为子分；参考回复没有可用短语时跳过 | 0.17 |
| AI 味命中 | 客服腔黑名单命中的类别数（自述 AI、希望帮到你、首先/其次/总之、书面腔、主动服务、祝福结尾等） | 命中越多扣得越多，命中数 ÷ 样例数 达到 1 时子分 0 | 0.10 |
| 长回复比例 | 非空行数 > 3 的样例占比；语料级比较参考与生成的占比 | 相差 30 个百分点时子分 0 | 0.09 |
| 禁忌词命中 | 从 `data/style-profile.json` 的 `taboo` / `tabooWords` / `custom.taboo` 读取；生成结果每命中一个词就整项 0 分 | 画像没有列表时跳过 | 0.08 |

补充说明：

- 高频短语取参考回复里重复出现的 2~4 字片段；没有重复时用最长的 2~3 字片段补足 5 个。它是「原话复用率」，不是语义相似度：改写得很像但用词完全不同，这项会低。
- AI 味黑名单是固定代码常量，见 `scripts/eval-style.js` 的 `AI_TONE_PATTERNS`。命中标签不会写进 `--json`，只记数量。
- 某项不适用（没有短语候选、画像没有禁忌词）时跳过，剩余权重按比例重新归一，不会拿 0 分凑数。终端会打印有效权重。
- 总分 = 各指标子分 × 权重后求和 ÷ 有效权重 × 100，保留一位小数。权重写死在脚本顶部，并有注释说明为什么这样分。
- 终端逐条表里的「得分」只用于定位哪条样例跑偏；最终看的是语料级总分，不是单条得分的平均。

## 怎么判断「更贴近本人」

这不是「跑一次高分就算赢」，而是一个同条件 A/B：

1. **固定条件**：同一模型、同一采样配置、同一份 `samples.json`、同一份 `data/style-profile.json`。只改一个变量（提示词、画像生成、人设配置）。
2. **先量噪声**：不改任何东西，连跑两次。同一配置的分数差就是这套模型 + 这套样例的随机波动。差值小于波动时，不要宣称改进。
3. **看总分，也看指标**：总分上升，并且下面三条至少满足两条，才算「更像」：
   - 平均句长、语气词密度、高频短语覆盖中至少两项朝参考值靠近；
   - AI 味命中没有增加；
   - 三个场景没有明显塌陷（逐条表里不能只有 work 变好，friend / family 大面积变差）。
4. **禁忌词必须是 0**。命中一次就整项 0 分；如果总分仍然很高，说明样例集或画像的 taboo 配置有问题，不是模型没问题。
5. **看方向，不看绝对值**：60 分不是「及格线」，只是默认的回归警报。不同人、不同样例集的分数不能互相比较；只比较同一套样例的前后两次。
6. **分数上涨但短语覆盖下降、AI 味上升**：通常是模型学会了「平均客服腔」而不是本人，按不通过处理。

建议把「改动前 / 改动后」两次的命令、模型名、总分和关键指标写进 PR 描述。不要把生成正文或完整指标 JSON 提交进仓库。

## 隐私要求

- 样例里禁止真实 wxid、群号、手机号、邮箱、公司真名；人名、公司、地点一律用「老王」「小李」「某公司」这类占位。
- `reference` 即使是本人真实回复，也必须先脱敏；不能确认是否敏感的，换成合成占位。
- `--check` 会复用 `scripts/privacy-scan.js` 的规则扫描每条样例，并额外检查真实公司名。CI / 提交前必须通过。
- 不把微信导出文件、聊天记录、生成结果、模型日志放进 `tests/fixtures/` 或 `docs/`。
- `--json` 只写指标与 id：没有参考正文、生成正文、短语列表、具体禁忌词。仍然建议写到 `artifacts/` 或仓库外，不要提交运行产物。
- 终端表格只显示差值和分数；脚本不会打印完整消息正文。

## 不做两段式生成

这套测评明确按「单段生成」设计：

- 每条样例只调用一次 `llm.complete`；
- 不做「先写草稿再让模型改写」；
- 不做自评、重排、best-of-N、二次润色；
- 不把参考答案塞回提示词让模型「参考着写」。

原因是两段式会改变产品行为和成本，也会让「像不像本人」的分数无法和线上回复对应。以后如果真的要加第二段生成，必须作为独立产品决策，先更新本文档和基线，再谈分数是否可比。

## 已知局限

- 只测单轮表达，不测多轮人设一致性、记忆准确性、事实正确性。
- 高频短语覆盖偏「原话复用」，对合理改写不友好；看总分时结合句长、语气词一起看。
- 模型输出本身不确定；单次分数有波动，必须同条件重复跑。
- emoji / 语气词是词法统计，测不出反讽、克制、亲疏关系这些语义层的东西。
- `--run` 会强制 `features.styleProfile=true`、`persona.styleScope=all`，否则默认 `owner` 作用域会跳过画像注入，测不到「分身」。其余配置沿用当前 `config.json`。
- `--run` 用非流式的 `llm.complete` 调用，和线上 `stream` 共用同一份 payload / 提示词构造，但不经过 pipeline 的复读重写和发送前过滤；测的是模型在给定提示词下的表达，不是最终发到微信的文本。
- 没有 `data/style-profile.json` 时提示词不会注入风格块，这时测的是基础人设，不是分身；脚本会打印提示，但不会替你生成画像。
